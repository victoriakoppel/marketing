# Текущий кинопрокат

Дашборд ежедневной аналитики кинопроката: текущий срез афиши и накопительная
динамика по дням. Статический сайт без сборки и без бэкенда — три файла
фронтенда плюс Python-сборщик, который раз в сутки складывает снимок в JSON.

## Быстрый старт

```bash
cd kinoprokat
python3 -m http.server 8000        # открыть http://localhost:8000
```

Из коробки показываются демо-данные за 14 дней: цифры синтетические, интерфейс
честно предупреждает об этом баннером. Пересоздать их:

```bash
pip install -r collector/requirements.txt
python collector/make_demo.py --days 14
```

## Как это работает

```
источник (сайт афиши)
        │  collector/collect.py — раз в сутки, 06:00 Алматы
        ▼
data/snapshots/YYYY-MM-DD.json     полный снимок дня, архив, не переписывается
        │  collect.py --rebuild
        ▼
data/latest.json  +  data/history.json
        │  fetch() при загрузке страницы
        ▼
index.html + app.js + styles.css
```

Снимки — источник истины. `latest.json` и `history.json` из них пересобираются,
поэтому их можно удалить и восстановить в любой момент: `--rebuild`.

## Сбор данных

Разбор страницы идёт от надёжного к хрупкому — первый сработавший способ выигрывает:

1. **JSON-LD** (`schema.org`: `ScreeningEvent`, `Movie`). Размечен самим сайтом,
   переживает редизайн. `ScreeningEvent` — это один сеанс: их количество и есть
   «сеансы сегодня», минимум по `offers.price` — «цена от», `aggregateRating`
   у `Movie` — оценка и число отзывов.
1a. **Обход карточек фильмов** (для Kino.kz). Со страницы афиши собираются
   ссылки вида `/ru/movie/12034`, каждая карточка открывается отдельно, и с
   неё читаются счётчик проданных билетов, реакции, цены и расписание.
   Разбор опирается на подписи, напечатанные для человека («билетов продано»,
   «₸», «Рецензии»), а не на имена CSS-классов: вёрстку переделывают часто,
   подписи — почти никогда. Между запросами выдерживается пауза.
2. **Состояние SPA** (`__NEXT_DATA__`, `__NUXT__`, `__INITIAL_STATE__`). Данные
   структурированы, но ключи у каждого сайта свои — маппинг пишется под сайт.
3. **CSS-селекторы** из `SOURCES` в `collect.py`. Последний рубеж, ломается при
   любой переверстке.

Прежде чем настраивать сбор, посмотрите, что источник вообще отдаёт:

```bash
python collector/collect.py --probe --source ticketon --city almaty
```

`--probe` печатает размер страницы, найденные типы JSON-LD, наличие состояния
SPA, число совпадений CSS-селектора и первые разобранные фильмы. По этому выводу
правится блок `SOURCES[...]["css"]` — все селекторы собраны в одном месте.

Боевой запуск:

```bash
python collector/collect.py --source ticketon --city almaty
```

## Про «билеты продано»

Kino.kz печатает счётчик прямо на карточке фильма: «632 836 билетов продано»
и рядом «+168 за последние 15 минут». Это открытая цифра, её и берём — поле
`total_sales`, помеченное `"sales_basis": "kino_kz_counter"`.

Что важно понимать про эту цифру: она **накопительная за весь прокат фильма**
по площадке Kino.kz, а не продажи за сутки. Отсюда два следствия:

* «Билетов продано» в шапке — итог с начала проката, а не за день;
* продажи за день — это **разница двух соседних снимков**, и считает её
  дашборд сам. Поэтому первая осмысленная цифра динамики появляется на
  второй день сбора.

Счётчик считает билеты, проданные через Kino.kz, — это не касса фильма
целиком, но для сравнения фильмов между собой и для отслеживания темпа
подходит.

Если источник счётчика не даёт, опорой становится занятость зала
(`maximumAttendeeCapacity` и `remainingAttendeeCapacity` у сеанса). Нет ни
того, ни другого — `total_sales` остаётся `null`, и дашборд честно
деградирует: прочерк вместо цифры, витрина переключается на сеансы и отзывы,
сортировка «по продажам» отключается. Выдуманных чисел в интерфейс не
попадает.

## Формат снимка

```jsonc
{
  "date": "2026-08-31",
  "collected_at": "2026-08-31T06:00:00+06:00",
  "city": "almaty",
  "source": "Ticketon",
  "strategy": "json-ld",        // как разобрали: json-ld | css | demo
  "is_demo": false,             // true → баннер-предупреждение в интерфейсе

      "id": "dyuna-chast-tretya",

    }
  ]
```

## Автоматизация

`.github/workflows/kinoprokat.yml` запускает сбор в 00:00 UTC (06:00 Алматы),
коммитит новый снимок и пересобранные `latest.json` / `history.json`. Запуск
руками — через **Actions → Run workflow** с выбором источника и города.

`.github/workflows/pages.yml` публикует сайт на GitHub Pages: после каждого
успешного сбора и при правках вручную. Единственная ручная настройка —
**Settings → Pages → Source: GitHub Actions**.

Обе задачи запускаются только из основной ветки репозитория: так устроен
GitHub, расписание и кнопка запуска работают лишь оттуда. Пока проект живёт
на отдельной ветке, ни то ни другое не сработает.

## Что стоит знать перед боевым запуском

- **Разбор не проверен на живом сайте.** В окружении, где собирался проект,
  исходящий доступ в интернет закрыт политикой сети, поэтому ни одну страницу
  Kino.kz открыть не удалось. Разбор карточки написан по скриншоту реальной
  страницы и закреплён тестом `collector/test_parse.py`, который сверяет
  результат с цифрами оттуда. Первый боевой запуск всё равно надо посмотреть
  глазами: адрес страницы афиши и способ выбора города — то, что проверить
  без доступа к сайту невозможно.
- **Уважайте источник.** Проверьте `robots.txt` и условия использования сайта,
  не наращивайте частоту: одного запроса в сутки хватает, весь смысл проекта —
  в ежедневной точке, а не в реальном времени.
- **История накапливается только вперёд.** Задним числом данные взять неоткуда,
  поэтому графики динамики оживают со второго сбора — до этого показывается
  явная заглушка, а не пустой прямоугольник.

## Проверено

Интерфейс прогнан в Chromium через Playwright на трёх состояниях данных:
14 дней истории, отсутствие продаж у источника, единственный первый снимок —
и в светлой, и в тёмной теме. Во всех случаях без ошибок в консоли.

Разбор карточки фильма закреплён тестом: `python collector/test_parse.py`.
