Источник 1. YouTube Analytics

Ядро дэшборда — примерно 95% объёма данных

установлено по коду

Опознаётся однозначно: подписи категорий лежат в данных на английском ровно в формулировках YouTube Studio — Browse features, Suggested videos, End screens, Hashtag pages, Related Shorts, Mobile phone, User specified. Плюс у каждой серии лежит channelId вида UCgMG7Rs… и seriesId — это идентификатор видео.

Источник 2. Продуктовая аналитика платформы Freedom Media

Всё, ради чего дэшборд существует: драйверы, уники, подписки, CPA

предположение о системе

Сами поля и их значения — факт из данных. Из какой системы они выгружены, в коде не указано: это внутренние продуктовые метрики платформы, значит BI / хранилище / продуктовая аналитика (GA4, Amplitude или собственный DWH). Ключевая улика — у каждого показателя рядом лежит дата снимка вида driversDate: "12.04" или "2026-05-12". Так выглядит цифра, переписанная из отчёта на конкретный день, а не поток из API.

ПолеСмыслПокрытие

Главный вывод по этому блоку. Дневная динамика есть только у драйверов. Подписки, уники платформы, CPA — точечные снимки. Именно поэтому в дэшборде «релизный режим» строится на драйверах, а всё остальное показано карточками с датой.

Источник 3. Трекер ссылок и атрибуция установок

Путь «ссылка под видео → установка приложения»

предположение о системе

В данных лежит готовая разбивка по четырём точкам назначения — это выгрузка трекера, а не YouTube:

destinations: { superapp: {clicks 2643, installs 123}, standalone: {clicks 42011, installs 12820}, website: {clicks 6300}, landing: null }

Клики по ссылкам может отдавать сокращатель или UTM-разметка в GA4; установки с разделением на Freedom SuperApp и отдельное приложение — это уже мобильная атрибуция (AppsFlyer, Adjust или внутренняя система). Поля linkClicks / appInstalls есть у 22 серий из 52 и снабжены датой в формате "12.04" — снова ручной перенос.

Источник 5. Яндекс Wordstat

Поисковый интерес к названию сериала

установлено по коду

Блок __wordstat__ у 5 проектов из 7, структура в точности повторяет ответ Wordstat: фраза, регион, период, помесячные записи.

{ phrase: "Мунай сериал", regionId: 159, regionName: "Казахстан", period: "monthly", entries: [{date, count, share}], total, latestDate }

Важная деталь: запросы в Google живыми данными не являются. В коде они при отсутствии значения вычисляются как yandexQueries × googleMultiplier, а множитель зашит в данные вручную (у Forever 29 — 2.4). Запросы на YouTube лежат отдельным числом в discoveryMetrics — вероятно, из Studio или стороннего сервиса, но происхождение в коде не отражено.

Источник 6. Калькулятор сценариев в Excel

Весь «релизный режим» вырастает отсюда

путь к файлу сохранён в данных

В блоке __releaseScenarios__ честно записан исходник:

"source": "/Users/maksimsalnikov/Downloads/success_calculator_Школьная_драма_Gen_Z_Teens_raw_2026-04-22.xlsx"

То есть модель живёт в Excel-файле на чьём-то ноутбуке, выгружается вручную и версионируется полем updatedAt. Пять сценариев — «Очень хорошо», «Хорошо», «Средне», «Плохо», «Очень плохо», каждый с полями hotCore, wideAudience, totalAudience, kpd, drivers, cpa, budget и удвоенным вариантом. Арифметика внутри простая и проверяется: драйверы = ЦА × КПД, бюджет = драйверы × CPA.

Источник 7. Threads + разметка тональности моделью

Соцслушание — только у одного проекта

установлено по коду

Блок __threadsPosts__ есть только у «140 баллов». Внутри — посты со ссылками на threads.net, метриками (likes, replies, reposts, forwards), временем сбора collectedAt и, что показательно, полями sentiment и reason — текстовым объяснением оценки на русском. Так выглядит разметка языковой моделью, а не счётчик площадки. Источник подписан как viral_posts_140_балл.xlsx: сначала парсинг, потом ручная сводка в Excel.

Что источником не является

Часть цифр в дэшборде выглядит как данные, но считается на месте — их не нужно нигде брать:

Признаки того, что сборка ручная

Это не придирка — от этого зависит, что чинить в первую очередь:

  • Серии названы по-разному в каждом проекте: «140 балл | 1 серия», «Мунай_s01_e01», «Улжан — 1 серия», «Умай - Серия 1». Единого справочника контента нет, ключ собирается вручную.
  • Дыры в покрытии: releaseDate есть у 29 серий из 52, reach — у 11, промо — у 6. Значит, часть выгрузок делали один раз и не повторяли.
  • Даты снимков в разных форматах — "12.04" рядом с "2026-05-12".
  • Платформа всегда одна — ключ "All". Селектор платформы в интерфейсе есть, а разделения данных по платформам нет.

Что нужно, чтобы собрать это заново

  1. YouTube Analytics API
    Даёт сразу 95% содержимого: просмотры, показы, удержание, демографию, источники, города, а через города — и карту регионов. Нужен доступ к каналу и список videoId по сериям. Единственный блок, который автоматизируется полностью и сразу.
  2. Выгрузка продуктовых метрик платформы
    Драйверы, уники, подписки, CPA. Здесь главный вопрос не технический, а организационный: нужна дневная гранулярность, а не снимок на дату — иначе «релизный режим» так и останется одной кривой драйверов.
  3. Справочник контента
    Одна таблица: проект, сезон, серия, дата релиза, videoId, id тайтла на платформе. Без неё любые две системы придётся склеивать руками, как сейчас.
  4. Трекер ссылок и атрибуция установок
    Клики и установки с разбивкой superapp / отдельное приложение / сайт / лендинг.
  5. Медиаплан и Wordstat
    Промо-охваты из отчётности агентства, поисковый интерес — из Wordstat. Оба спокойно живут в Google Sheets и обновляются раз в неделю: дневная точность здесь не нужна.
  6. Модель сценариев
    Перенести success_calculator.xlsx из чьих-то «Загрузок» в общую таблицу с версией. Формулы там простые, весь риск — в том, что файл существует в одном экземпляре у одного человека.
Если коротко: данных из внешних систем всего два вида — YouTube и продуктовая аналитика платформы. Всё остальное — таблицы, которые ведут люди. Автоматизация первых двух закрывает большую часть дэшборда, остальному достаточно одной общей Google-таблицы вместо файлов на ноутбуках.

Разбор сделан по исходнику страницы, присланному в .docx. Пометка «установлено по коду» означает, что вывод следует прямо из данных или логики файла; «предположение о системе» — что состав полей известен точно, а конкретный продукт-источник в коде не назван и восстановлен по характеру данных.
